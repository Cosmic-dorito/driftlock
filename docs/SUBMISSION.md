# Requirements compliance

This document maps every stated requirement of the Applied Materials *Drift-Sense* problem
statement onto the artefact that satisfies it, so that a reviewer can verify coverage without
reading the source.

Requirements are transcribed from three primary sources:

1. `Problem Statement 02 — Applied Materials, PS 2` — the official problem statement
2. `Idea Submission Template, Hackathon 2026` — the mandatory presentation template
3. The organiser question-and-answer session, *Applied Materials Problem Statement: Key Concepts*

Where a requirement derives from the spoken session rather than a written document, this is stated
explicitly. A spoken clarification is weaker evidence than a published slide and is treated as such
throughout.

---

## 1. Evaluation criteria

From the problem statement:

| Weight | Component |
|---|---|
| 50% | Inference results — correct coordinates on the evaluation data, including computation time |
| 30% | Augmentation code producing realistic SEM imagery of FinFET/DRAM structures, justified from literature |
| 10% | Root-cause identification and explainability on failure cases |
| Bonus | Equivalent capability demonstrated on RGB optical-microscope imagery |

### Accuracy is assessed on a graded tolerance ladder

The question-and-answer session established that accuracy is not assessed at a single threshold.
Predictions are scored at successively tighter tolerances — 5 px, 4 px, 2 px, 1 px, and sub-pixel —
and the proportion passing at each is recorded.

This has a direct consequence for method design. The reference implementation supplied with the
problem statement emits a coordinate of the form *integer + 50.0*, and therefore carries a
half-pixel quantisation floor: it cannot register on the sub-pixel rung under any circumstances.
Sub-pixel refinement is accordingly not a refinement of the result but a precondition for scoring
at the tightest tolerances.

Measured performance against that ladder is reported in **[`docs/RESULTS.md`](RESULTS.md)**, whose
headline section is generated directly from `results/`.

It is deliberately not reproduced here. A figure stated in two places is a figure that can disagree
with itself after the next measurement, and this project has already corrected several documents
that drifted apart in exactly that way. This document states requirements and points at the evidence;
it does not restate measurements.

### Computation time

The question-and-answer session characterised computation time as an order-of-magnitude criterion
rather than a fine-grained one: a difference between one second and 1.2 seconds was described as
immaterial, whereas a difference between one second and ten seconds was not. Measured localization
time is approximately 0.6 s per 1000×1000 pair on a single CPU core.

## 2. Presentation

The mandatory template is used unmodified in structure. Its first slide carries instructions and is
marked for removal before submission, which leaves exactly the nine slides onto which the problem
statement maps content:

| Template slide | Problem-statement mapping | Content |
|---|---|---|
| 1 | Team Details | Team, members, institution, contact |
| 2 | Problem Statement Addressed | Drift-Sense; why navigation-error recovery matters |
| 3 | Idea Description | Architecture choice, method family, comparison with template matching |
| 4 | Proposed Solution | Generator design, localization pipeline, citations |
| 5 | Innovation and Uniqueness | Handling of periodic ambiguity and the 10× scale difference |
| 6 | Results | Accuracy, computation time, one success and one failure case |
| 7 | Technology and Feasibility | Stack, hardware, generation and inference time, model size |
| 8 | GitHub and Video Link | Repository link |
| 9 | References | Citations supporting augmentation and noise choices |

**A discrepancy is recorded rather than resolved silently.** The template's instruction slide
suggests a limit of six to seven slides, while the problem statement specifies a nine-slide mapping
and the template itself contains nine content slides. The problem statement is track-specific and
has been followed.

The deck is generated by `scripts/make_submission_deck.py`, which reads every quantitative figure
from `results/` at build time. A plain-text extract is maintained at `docs/DECK_CONTENTS.md`.

## 3. Repository contents

| Requirement | Artefact |
|---|---|
| Complete setup instructions permitting independent reproduction | `README.md` |
| Dataset generator, standalone, parameterised by architecture, sample count and output directory, recording ground-truth centres | `generate_dataset.py` |
| Localization inference script, standalone, accepting reference and search image paths and emitting a predicted centre | `localize.py` |
| Deep-learning weights, loaded automatically | Not applicable — the method involves no training |
| Training script or notebook | Not applicable |
| Complete dependency specification ("complete pip freeze output") | `requirements-freeze.txt` — the exhaustive freeze. `requirements.txt` is the curated runtime subset and is what README.md instructs a reviewer to install |
| Citation documents corresponding to the presentation | `docs/REFERENCES.md` |

The problem statement identifies the inference script as the most important file in the repository,
notes that it will be executed directly on evaluation data, and requires that it run without manual
modification. Accordingly:

- The script emits exactly one line to standard output — the coordinate — with all diagnostics
  directed to standard error, so that it composes with an automated harness.
- Both `.png` and `.npy` inputs are accepted directly. A separate conversion utility
  (`scripts/npy_to_png.py`) is provided for visual inspection, but conversion is never a
  precondition for scoring. `tests/test_npy_io.py` asserts that the two input forms yield identical
  coordinates.
- Batch operation over a manifest or a directory requires no source modification.

## 4. Dataset

The problem statement requires a minimum of 30 representative evaluation cases and emphasises
diversity over volume. This submission reports 100 evaluated pairs across three splits, of which one
is a held-out architecture never used during development, supported by a further 750 pairs across 25
stress operating points and 200 pairs reserved for parameter selection.

**All 100 reported pairs and their ground truth are committed**, so every reported figure is
recomputable from the repository alone by running `scripts/audit_results.py`. This is deliberate:
a number that only its authors can check is not evidence. The tuning and stress splits are not
committed — nothing reported depends on them, and they are regenerable from the seeds recorded in
the README.

Generated variation covers magnification ratio, rotation, dose, detector noise, beam spot size,
raster shear and jitter, barrel distortion, gamma, vignetting, charging artefacts, speckle and
impulse noise. The question-and-answer session confirmed that evaluation data will include rotation
of one to two degrees, variation about the nominal 10:1 ratio, defocus and astigmatism, corner
falloff, charging artefacts, and a search image noisier than the reference.

## 5. Claims discipline

Every quantitative claim in the presentation and the documentation is generated from `results/`.
`scripts/verify_submission.py` extracts each numeric literal from the deck and fails the build if it
cannot be located there, which prevents a figure from surviving a change to the measurement that
produced it.

Two claims are deliberately qualified:

**Computation time is certified as of 18 August.** The benchmark applies two health gates to its
own measurement and the recorded run passes both: baseline control **18.8 ms** against a 22 ms
quiet-machine reference, and p95/p50 dispersion **1.145** against a 1.18 threshold. The file records
`absolute_ms_representative, yes`.

Earlier runs in the same session failed the control gate at 86–88 ms and were reported as such
rather than quoted. That was genuine thermal load from a long robustness sweep, not a property of
the method: the threshold was never widened to accommodate a number, and the measurement was simply
repeated once the machine was idle.

**The closest-to-centre tie-break is implemented but not enabled by default.** The problem statement
specifies that where several regions match, the one closest to the search-image centre should be
returned. This rule is implemented (`select_by_centre_rule`) and reachable by configuration, but is
disabled by default because it is measurably harmful on this data. The comparison is reported as a
row of the ablation table in `results/ablation.md` ("centre rule on the default"), alongside every
other stage that was evaluated and rejected. The deviation is deliberate, measured, and recorded
rather than concealed.
